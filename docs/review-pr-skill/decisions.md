# review-pr skill 設計判断の根拠

「なぜそう設計したか」をまとめる。構造そのものは [`architecture.md`](architecture.md)、出力仕様は [`output-format.md`](output-format.md) を参照。

## なぜレビューを subagent に委譲するのか（最重要）

親エージェント（skill 実行者）がレビューまで行うと、**自分の実装コンテキスト**がバイアスになる:

- 自分の実装を正当化する方向に評価が歪む。
- 「意図はこうだから問題ない」と、diff だけからは読み取れない前提で判断してしまう。

そこでレビューを**別コンテキストの `pr-reviewer` subagent** に必ず委譲する。subagent は実装履歴を引き継がず、渡された diff と参照可能なコードからのみ判断するため、第三者の目線が構造的に担保される。

## なぜ author 等を渡さないのか

- **PR 作成者（author）**: 「シニアが書いたから OK」のような権威バイアスを避けるため。
- **ヘッドコミット SHA**: 親が投稿時に使う情報で、レビュー判断には不要。情報を絞ることで subagent の関心をレビューに集中させる。
- **親の実装意図・経緯**: これを渡したらコンテキスト分離の意味が消える。客観性の核心。

逆に **PR 本文（body）は渡す**。これは人間レビュアーも読む公開情報で、変更の目的理解に必要だから。「内部的な実装経緯」とは区別する。

## なぜ JSON の内部キーを変えないのか

重大度の表示ラベルは「必須/推奨/任意/提案」に変更したが、JSON キー（`criticalCount` / `importantCount` / `minorCount` / `suggestionCount`）は**内部識別子としてそのまま維持**した。

理由: キー名まで変えると、親のパース処理と subagent の出力契約を同時に追従させる必要が生じる。**表示（人間向け）と内部表現（機械向け）を分離**しておくと、ラベルの文言は安全に変えられる。

## なぜ絵文字を使わないのか

重大度・カテゴリ・見出しを含め、装飾用の絵文字を一切使わない。すべてテキスト表現。

理由: このプロジェクトのオーナーは、絵文字混じりの Markdown は「AI が生成した感」が出るとして好まない。重大度マーカーのような機能的記号も例外にしない、という方針。元の skill は重大度・カテゴリを絵文字で表現していたが、移植時に全廃した（経緯は [`migration.md`](migration.md)）。

## 指摘の質に関する方針

- テーブルは重大度の高い順、同レベル内は影響範囲が大きい順。
- **任意／提案は合計 2〜3 件以内**。軽微な指摘を 10 件並べるより、必須級を 1 件示す方が価値が高い。
- **指摘ゼロも正しい結果**。問題が無ければ無理に作らない。
- 推測・憶測の指摘はしない。確証あるもののみ。
- 「なぜこう書いたか分からない」コードを安易に間違いと決めつけない（背景を知らないため判断保留）。

## このリポジトリ固有のレビュー観点を導く方針

`pr-reviewer` には汎用観点ではなく、変更内容に応じた**このリポジトリ特有の観点**を導かせる。構成（`firmware/` C++、`daemon/` TypeScript、`assets/clawd/` 生成、`docs/superpowers/` 設計書）を手がかりとして渡している。例:

- ファーム（C++）変更 → LittleFS 容量／パーティション、`loop()` 内のブロッキング
- daemon（TS）変更 → ポーリング間隔とファーム挙動の整合、`*.test.ts` の追従
- アセット生成変更 → `convert.mjs` の出力形式（`window.PRESET` / `window.FRAMES+PAL`）とファーム期待値の一致
- セキュリティ → `firmware/include/secrets.h` 相当の秘匿情報が diff に直書きされていないか
