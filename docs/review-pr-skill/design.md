# review-pr skill 設計

`/review-pr` skill と `pr-reviewer` subagent の設計・アーキテクチャ・設計判断の根拠をまとめる。

## 1. 目的と非目的

### 目的

- GitHub PR を Claude が客観的にレビューし、結果を **PR コメントとして自動投稿**する。
- 人間レビュアーが確認する「下地」を機械的に整える。

### 非目的

- 人間レビューの置き換えではない。最終判断は人間が行う。
- コードの自動修正は行わない（指摘のみ。修正は別作業）。
- CI でのゲート用途は想定していない（手動起動のアシスト）。

## 2. 全体アーキテクチャ

2 つの役割を明確に分離する。

```
ユーザー
  │  /review-pr <PR番号>
  ▼
親エージェント（skill 実行者）= オーケストレーション専任
  - gh CLI で PR 情報・diff を取得
  - subagent への入力プロンプトを構築
  - subagent から JSON を受け取る
  - gh CLI で PR にコメント投稿
  - CLI へ結果報告
  │  プロンプト（リポジトリ情報・PR本文・diff）
  ▼
pr-reviewer subagent = レビュー分析専任（コンテキスト分離）
  - Read / Glob / Grep で関連コードを確認
  - 客観的にレビュー
  - 構造化 JSON を返す（編集・投稿はしない）
```

### なぜ 2 役に分けるのか（最重要の設計判断）

レビューを **必ず subagent に委譲する**のは、**親エージェントの実装コンテキストを持ち込ませない**ため。

親エージェントが「自分がこのコードを書いた／こう意図した」を知っていると、レビューに次のバイアスが入る:

- 自分の実装を正当化する方向に評価が歪む
- 「意図はこうだから問題ない」と、diff だけからは読み取れない前提で判断してしまう

subagent は**別コンテキスト**で起動され、渡された diff と参照可能なコードからのみ判断する。実装履歴を引き継がないので、第三者の目線が担保される。

### 親と subagent の責務分界

| | 親エージェント | pr-reviewer subagent |
|---|---|---|
| PR 情報・diff 取得 | 担当（gh CLI） | しない |
| レビュー分析 | しない | 担当（Read/Glob/Grep） |
| レビュー本文生成 | しない（加工も禁止） | 担当 |
| コメント投稿 | 担当（gh CLI） | しない |
| 使えるツール | Bash, Read, Glob, Grep, Agent | Read, Glob, Grep のみ |

subagent に Bash/Edit/Write を与えないのは、「分析専門」であることを構造的に保証するため。投稿や副作用は親だけが持つ。

## 3. subagent に渡すもの／渡さないもの

入力設計は「人間レビュアーが通常見る公開情報だけを渡す」という原則に従う。

### 渡す

- リポジトリ情報（owner/repo、PR 番号、タイトル、base/head ブランチ、URL）
- **PR 本文（body）**: 変更の目的を理解するための公開情報。人間レビュアーも読む
- **diff**（`gh pr diff` の出力全体）
- リポジトリ構成の手がかり（どこに何があるか）

### あえて渡さない

| 渡さないもの | 理由 |
|---|---|
| PR 作成者（author） | 「シニアが書いたから OK」等の権威バイアスを避ける |
| ヘッドコミット SHA | 親が投稿時に使う情報。レビューには不要 |
| 変更ファイル一覧・行数 | diff から自分で読み取れる |
| 親の実装意図・経緯 | 客観性を損なう核心。これを渡したら分離の意味がない |

## 4. 出力契約（構造化 JSON）

subagent は **JSON 1 つだけ**を返す。親はそれをパースして投稿する。

```json
{
  "topLevelComment": "Markdown 文字列",
  "inlineComments": [
    { "path": "daemon/src/poller.ts", "line": 42, "side": "RIGHT", "body": "Markdown 文字列" }
  ],
  "summary": { "criticalCount": 0, "importantCount": 1, "minorCount": 2, "suggestionCount": 1 }
}
```

- `topLevelComment`: PR 全体への要約・影響範囲・リスク・観点・指摘テーブル
- `inlineComments`: 行を特定できる指摘。`line` は **ファイル内の行番号**（diff ハンクヘッダ `@@ -a,b +c,d @@` の `+` 側）。diff 出力自体の行カウントではない
- `summary`: 重大度別件数。「主要な指摘」テーブルの行数と一致させる

構造化 JSON にする理由は、親が決定的にパースして gh CLI へ流し込めるようにするため。自然文だと投稿の自動化が壊れやすい。

## 5. 重大度モデル（4 段階）

「何をすべきか」起点のテキストラベルを使う。**絵文字は使わない**（後述）。

| ラベル | 意味 | 対応 JSON キー |
|---|---|---|
| 必須 | バグ・脆弱性・明らかに動かない・データ損失。マージ前に必ず直す | `criticalCount` |
| 推奨 | 設計上の問題・明確な改善余地・テスト不足。強く推奨 | `importantCount` |
| 任意 | スタイル・軽微な改善・命名の一貫性。余裕があれば | `minorCount` |
| 提案 | アイディア・強い推奨ではない代替案 | `suggestionCount` |

JSON キー（`criticalCount` 等）は**内部識別子としてそのまま維持**し、表示ラベルだけ日本語にした。キー名まで変えると親のパース処理と一致させる手間が増えるため、表示と内部表現を分離している。

### 指摘の質に関する方針

- テーブルは重大度の高い順、同レベル内は影響範囲が大きい順。
- **任意／提案は合計 2〜3 件以内**。軽微な指摘を 10 件並べるより、必須級を 1 件示す方が価値が高い。
- **指摘ゼロも正しい結果**。問題が無ければ無理に作らない（「主要な指摘」テーブルを省略し、`inlineComments` は空配列、`summary` は全て 0）。
- 推測・憶測の指摘はしない。確証あるもののみ。
- 「なぜこう書いたか分からない」コードを安易に間違いと決めつけない（背景を知らないため判断保留）。

## 6. 装飾方針: 絵文字を使わない

重大度・カテゴリ・見出しを含め、**装飾用の絵文字を一切使わない**。すべてテキストで表現する。

理由: このプロジェクトのオーナーは、絵文字混じりの Markdown は「AI が生成した感」が出るとして好まない。重大度マーカーのような機能的記号も例外にしない、という方針。

（元の skill は重大度を絵文字（赤丸・橙丸など）、カテゴリを絵文字で表現していたが、移植時に全廃してテキスト化した。）

## 7. 投稿の安全設計

親が gh CLI でコメントを投稿する際、本文には Markdown（バッククォート、`$`、引用符など）が含まれる。シェルで安全に渡すための工夫。

### トップレベルコメント

```bash
gh pr comment <num> --repo <owner>/<repo> --body-file - <<'EOF'
（本文をそのまま）
EOF
```

- `--body-file -` で **標準入力**から本文を読ませる（一時ファイル不要）。
- ヒアドキュメントの開始タグを **シングルクォート**（`<<'EOF'`）にすることで、本文中の `$変数` や `` `コマンド` `` がシェルに評価されない。リテラルとして安全に渡る。
- 本文に `EOF` が出現する場合に備え、別センチネル（例: `__CLAUDE_REVIEW_END__`）も使える。

### インラインコメント

```bash
gh api -X POST repos/<owner>/<repo>/pulls/<num>/comments --input - <<'EOF'
{ "body": "...", "commit_id": "<headRefOid>", "path": "<path>", "line": <line>, "side": "RIGHT" }
EOF
```

- `--input -` で標準入力から JSON を読ませる。
- JSON 文字列値は正しくエスケープ（改行 `\n`、`"` は `\"`、`\` は `\\`）。subagent の応答から値を取り出して新しい JSON に埋める際は、**JSON エスケープを維持したまま**埋める。
- `side` は通常 `RIGHT`（追加・変更行）、削除行への指摘なら `LEFT`。

## 8. エラーハンドリング方針

| 状況 | 対応 |
|---|---|
| 対象 PR が見つからない | エラーで終了し、PR 作成か番号指定を促す |
| gh 認証失敗 | `gh auth status` を案内（remote は github.com） |
| subagent の応答が不正な JSON | リトライ 1 回。2 回目も失敗なら生応答を出して終了 |
| 指摘ゼロ | トップレベルのみ投稿、インラインはスキップ |
| インライン投稿失敗（該当 line が diff に無い等） | その 1 件をスキップして続行、失敗件数を報告 |
| 大規模 diff | 重要ファイル優先で渡し、「一部は概観のみ」と明記 |
| API レート制限 | 待ってリトライ、駄目なら通知 |

## 9. 親が守るべき不変条件

- **subagent の結果を加工しない**。「優しい表現に」「この指摘は不要」といった介入をしない。親の仕事は「投稿する」ことであり「レビューする」ことではない。
- ローカルのチェックアウトブランチが PR の head と異なる場合、subagent が誤ったローカルファイルを読む可能性があるため、切り替えるか、diff 優先の警告を subagent プロンプトに添える。

## 10. このリポジトリ固有のレビュー観点

`pr-reviewer` は汎用観点ではなく、変更内容に応じた**このリポジトリ特有の観点**を導くよう設計している。構成（`firmware/` C++、`daemon/` TypeScript、`assets/clawd/` 生成、`docs/superpowers/` 設計書）を手がかりとして渡しており、例えば:

- ファーム（C++）変更 → LittleFS 容量／パーティション、`loop()` 内のブロッキング
- daemon（TS）変更 → ポーリング間隔とファーム挙動の整合、`*.test.ts` の追従
- アセット生成変更 → `convert.mjs` の出力形式（`window.PRESET` / `window.FRAMES+PAL`）とファーム期待値の一致
- セキュリティ → `firmware/include/secrets.h` 相当の秘匿情報が diff に直書きされていないか
