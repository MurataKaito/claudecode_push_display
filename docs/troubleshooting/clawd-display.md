# キャラ表示のつまづき記録（Clawd ドット絵）

「M5 のディスプレイに Clawd を思った通りに載せる」までに踏んだ問題と、その原因・対処・発見。パイプライン全体（ClaudePix HTML → `convert.mjs` → `render.py` → PNG → LittleFS → ファーム描画）のどこで何が起きたかを残す。

根拠は git のコミットと、開発セッションの会話記録（2026-06-04）。引用は当時の発言の原文ママ。

```
ClaudePix HTML ─ convert.mjs ─→ frames JSON ─ render.py ─→ PNG ─ uploadfs ─→ LittleFS ─ display.cpp ─→ 画面
     (取得)        (抽出)                       (描画)              (書込)                  (drawPng)
```

## 1. そもそも「本物の Clawd」を載せられない（最大の山場）

- **問題**: 「Clawd を表示して」に対し、最初に出てきたのは自作の「Clawd っぽい」顔。欲しいのは本物の見た目だった。

  > 「ん、思ってた要件と違うくて、っぽくではなく本物ってことな。画像みたいなやつをclawdってゆうのではないのか」

  その後も「自作じゃなくてそのままのやつがいいねんけど」「完璧な再現をしてほしい」と要求したが、Claude 側は著作権を理由に公式絵の複製を拒否し、約 45 分膠着した。
- **原因**: 公式アセットの再現を AI に直接描かせる方針が成立しなかった。一方で「PNG を置けば 1:1 で表示できるパイプライン」自体は先行して構築済みだった（テスト用の円画像で確認）。足りないのは「正規に取得できる本物のフレームデータ」だけだった。
- **対処（ブレークスルー）**: ユーザー自身が変換元になるサイトを発見。

  > 「あった、https://claudepix.vercel.app/ これ使えそう」

  当初は MP4 → ffmpeg 分解案だったが、「htmlは動きつきでcopyできるっぽいで」の指摘で HTML 取得へ方針転換。さらに 13 個を手作業コピーする段取りを進めている途中、ClaudePix の `app.js` 内に MANIFEST 配列が見つかり、`animations/<名前>` から **13 クリップ全部を自動取得**できた。`convert.mjs`（Node でエンジンを実行してフレーム計算）+ `render.py`（PNG 化）の変換パイプラインが成立し、実機に look_around が表示されて決着。
- **発見・教訓**:
  - 「AI に絵を描かせて再現する」のではなく「**正規の配布物を機械的に変換する**」構図にすると、忠実度と権利面が同時に解決する。
  - 膠着したら入力（ソース）側を変える。突破口は実装ではなくデータの入手経路だった。
  - 並行して受け側パイプライン（uploadfs → LittleFS → 表示）を先に完成させておいたことで、ソースが見つかった瞬間に一気通貫した。

## 2. PNG フレームが右下にずれて表示される

- **問題**: 中央に寄せたつもりが、逆に右下へずれた。

  > 「さっき真ん中に寄せるみたいなことしたせいで、右下にあるわ」
- **原因**: `drawPng()` の位置合わせに `middle_center`（中央寄せの datum 指定）を使ったが機能せず、(160,100) を左上として描画されていた。
- **対処**: フレームは 200×200 固定と分かっているので、水平中央 = (320-200)/2 = 60 を自前で計算し、絶対座標 (60, 0) に固定。

  ```cpp
  g_cv.drawPng(buf, sz, 60, 0);
  ```

  コミット `a7d6d47`（`firmware/src/display.cpp`）
- **発見・教訓**: M5Unified の `drawPng()` は引数の順序・datum 定数の意味が非自明。凝った位置指定に頼らず、絶対座標を自分で計算して渡す方が確実。

## 3. キャラの周囲に四角い縁が浮いて見える

- **問題**: キャラの周りに PNG の矩形がうっすら見える。

  > 「このキャラクターの周りに四角があると思うがこの色と同じ背景にして」
- **原因**: 画面の塗りつぶしが `TFT_BLACK`（0x0000 = 真っ黒）、PNG の背景が `#0f0f0f`（ClaudePix の背景色。わずかに明るい黒）で、微妙な色差が矩形の縁として知覚された。
- **対処**: `fillScreen` を PNG と同じ色に統一。

  ```cpp
  g_cv.fillScreen(M5.Display.color565(15, 15, 15));  // PNG背景(#0f0f0f)と同色
  ```

  コミット `ddd05b7`（`firmware/src/display.cpp`）
- **発見・教訓**: 「黒」と「ほぼ黒」は実機の液晶では見分けられてしまう。素材の背景色と画面の塗り色は、論理名（TFT_BLACK）ではなく実値で揃える。

## 4. アニメ HTML の形式が 2 種類あり、片方が変換できない

- **問題**: ClaudePix から取得した HTML のうち、DJ 系の新しいアニメだけ `convert.mjs` の変換が失敗した。
- **原因**: ClaudePix のアニメ定義に 2 形式が混在していた。
  - 旧形式: `window.PRESET.frames`（creature-engine ベース。セル値 0=空 / 1=体 / 2=目、固定 2 色）
  - 新形式: `window.FRAMES` + 多色パレット `window.PAL`（自己完結型）

  初期の `convert.mjs` は `PRESET` しか見ておらず、`FRAMES` 形式で即エラー終了していた。
- **対処**: 両形式を判定して取り込むよう拡張。`PRESET` があれば旧形式として固定パレット、無ければ `FRAMES`+`PAL` を読む。engine 加工が失敗しても処理を続けるフォールバックも追加。

  コミット `6fd6ddd`（`assets/clawd/convert.mjs`）
- **発見・教訓**: 外部サービスのデータ形式は「最初に見たサンプル」が全てではない。形式判定とフォールバックを最初から想定しておくと、後から来る別形式に壊されない。

## 5. ドット絵がのっぺりして本家と違う

- **問題**: 表示はできたが、本家 ClaudePix のドット質感と違いベタ塗りに見えた。

  > 「https://claudepix.vercel.app/ これの通りにdot絵っぽくね」
- **原因**: 本家は各ドットに inset 影（内側の薄い枠）がある質感だが、初期の `render.py` はベタ塗り。さらに多色パレット（DJ 系）にも非対応で、固定色（体=#CD7F6A）に潰れていた。
- **対処**: パレット値 → RGB のマッピングに書き換え、1 ドットずつ inset 影風の縁を付けて全クリップを再生成 → uploadfs。明るい色はそのまま、暗めの色は 0.7 倍した縁にする。

  ```python
  v = g[r][c]
  rgb = pal[v] if 0 <= v < len(pal) else None
  if rgb is None: continue
  edge = rgb if max(rgb) > 235 else tuple(int(x*0.7) for x in rgb)
  d.rectangle([x0, y0, x0+CELL-1, y0+CELL-1], fill=rgb, outline=edge)
  ```

  コミット `5076a3a`（`assets/clawd/render.py`）
- **発見・教訓**: ドット絵の「らしさ」は色数と影（縁）の付け方で決まる。単に表示できるだけでは本家の見た目にならず、質感の再現（inset 影）まで含めて移植と言える。

## 6. 長いアニメがフレーム数上限に収まらない

- **問題**: アニメの尺が長いとフレーム数が増え、全クリップを LittleFS に収めるのが難しくなる。最大フレーム数は 48 → 24 → 16 と段階的に絞られた。開発中、13 クリップで 936KB に達して容量懸念が出た場面もある（LittleFS パーティションが約 3.5MB と判明して解消）。
- **原因**（推測を含む）: 固定サンプリング間隔 dt=180ms で切り出すため、フレーム数は尺に比例する。13 クリップを収め、読み込み・切替の性能も保つ必要から、1 クリップ最大 16 フレームに制限したと推測される。

  ```python
  N = max(1, min(16, round(total / dt))); step = total / N
  ```
- **対処**: 上限 16 フレーム + `optimize=True` で PNG を圧縮し容量に余裕を確保。コミット `5076a3a` / `671371a`（`assets/clawd/render.py`）
- **発見・教訓**: 組込みでは「アニメの忠実度」と「フラッシュ容量・性能」のトレードオフが避けられない。dt 固定 + フレーム上限という割り切りで全クリップを同一速度に統一した。フレームごとの hold（表示時間）の忠実再現は TODO として残っている。

## 7. FS だけ更新するとキャラが出ない（ファームとの不整合）

- **問題**: ある時点からドット絵が消え、フォールバック（コード描画の簡易顔）に戻った。開発中に二度発生している。
- **原因**: ファイル名 prefix の移行（`idle0.png` → `breathe0.png` など）の途中で、FS は新名なのにファームの `PFX[]` 配列が旧名を探しに行き、見つからずフォールバックしていた。FS とファームのどちらか一方だけ更新すると不整合になる。
- **対処**: `/state` にデバッグ情報を追加して「FS に何があり、ファームが何を探しているか」を見える化 → 新ファーム書き込みで復旧（当時のログ: 「png=1 active=look」）。手順書に「**FS とファームはセットで更新**」を明記。

  記載先: `firmware/data/README.md`, `assets/clawd/README.md`
- **発見・教訓**: アセット名はファームとデータの「暗黙の契約」。名前を変える変更は両側に波及することを手順で担保する（コードでの自動検出は未実装）。表示系の不具合は目視だけだと原因が絞れないので、`/state` のような診断エンドポイントに内部状態を出すのが復旧の近道。
