# タッチ操作のつまづき記録

M5 Core2 のタッチ操作（使用率表示・タップ承認）で思い通りに動かなかった問題の記録。根拠は git のコミットと開発セッションの会話記録（2026-06-04）。引用は当時の発言の原文ママ。

## 1. ダブルタップがなかなか認識されない → 最終的にシングルタップ化

- **問題**: 画面を 2 回タッチして使用率を表示する機能が反応しない。

  > 「2回タップでできないな」

  `/state` を見ると touch カウンタは増えている（タッチ自体は検出されている）のにダブルタップが成立しない、という状態だった。
- **原因**: 二段構え。
  1. ジェスチャ判定の閾値が人間の操作実態に対して厳しすぎた。

     | パラメータ | 初期値 | 意味 |
     |---|---|---|
     | `tapMaxMs_` | 300ms | 押下がこれ以下でないとタップ扱いにならない |
     | `doubleMs_` | 400ms | 1 回目から 2 回目までの猶予 |
     | `swipeThresh_` | 40px | これ以上動くとスワイプ扱い |

  2. 閾値を緩和（700ms / 800ms / 55px、コミット `686fdb2`）しても、なお「出ないな」。アニメ描画が重くてメインループが遅く、素早い 2 連打を取りこぼしている、と推定された。
- **対処**: 厳密なダブルタップに依存する設計をやめ、**シングルタップでも使用率を表示**する仕様に変更。あわせてジェスチャ診断（`g_lastGesture`）を `/state` に公開し、実機で「どう判定されたか」を確認できるようにした。

  コミット `686fdb2`（`firmware/lib/gesture/gesture.h`）、`0010235`（シングルタップ化 + 診断公開）
- **発見・教訓**:
  - タッチ UI の使いやすさは机上では分からない。実機で「自分の自然な操作」が判定に入るかを確かめる。
  - 閾値チューニングで粘るより、**操作要件そのものを緩める**（ダブル → シングル）方が確実なことがある。描画負荷とポーリング頻度の相互作用は閾値では直らない。
  - 判定結果の見える化（`/state` の `g`）があると調整が圧倒的に速い。

## 2. 承認画面で意図せず「拒否」になる／そもそも反応しない

- **問題**: PreToolUse フックの承認画面（「CLAUDE Bash OK?」、タップ=許可 / スワイプ=拒否）で、タップしても進まない・許可したつもりが拒否扱いになる。当時の発言は端的に:

  > 「待ってるのだのまま」
  > 「出ない」
- **原因**: 複数要因の連鎖（ネットワーク要因は [`network-mdns.md`](network-mdns.md) 参照）。タッチに関する要因は、単発タップの判定が厳しく（押下 300ms 超で NONE 扱い）、「タップとダブルタップだけ許可・他は拒否側」という判定構造だったこと。長押し気味のタップや判定のブレが暗黙の拒否に落ちていた。

  ```cpp
  // 初期実装の構造
  if (g == GESTURE_TAP || g == GESTURE_DOUBLETAP) allow();
  else if (g == GESTURE_SWIPE) deny();
  // それ以外 → 実質 deny に流れる
  ```
- **対処**: 判定を反転し、「**スワイプのみ拒否、それ以外（タップ・ダブルタップ・長押し）は全部許可**」に変更。最終的に許可・拒否の両ルートを実機で確認して決着。

  ```cpp
  if (g == GESTURE_SWIPE) deny();
  else allow();
  ```

  コミット `e739a20`（`firmware/src/main.cpp`）
- **デバッグ上の発見**: シリアルログでの調査は空振りした（`M5.begin()` が `Serial.begin()` を呼ばずログが出ない）。HTTP の `/state` エンドポイントに診断カウンタを載せる方式へ切り替えたのが転機で、以後の表示・タッチ問題すべての調査基盤になった。
- **発見・教訓**: 誤判定のコストが非対称な UI（誤許可 < 誤拒否でタスク中断）では、コストの大きい側の判定条件を「明確で意図的なジェスチャ」1 つに限定し、残りは安全側（許可）に倒す。組込みのデバッグはシリアルに固執せず、既にある通信路（HTTP）に診断を載せる。
